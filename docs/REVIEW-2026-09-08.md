# Review — 8 September 2026

Prompted by: *"it asks me to add my name, and then nothing works."*

I reproduced that exactly, then went through the app page by page looking for anything
else that would fail the same way — quietly, with nothing for the player to act on.
**Nine issues found, all nine fixed.** One of them I introduced while fixing another and
caught during verification; it is listed too.

---

## First: why nothing worked

**The server was never deployed.** Not by me, not anywhere. I wrote the Dockerfile, the
Fly config and the Render blueprint, but no deploy was ever run, and
`zema-server.fly.dev` — which appeared in my earlier instructions — was a placeholder that
resolves to nothing.

So the client on Vercel was doing exactly what it was built to do: falling back to
`http://localhost:3001`, which from a browser means *your own laptop*, which has nothing
listening on the public internet.

That explains the symptom. It does **not** excuse it, because the app should have told you
that. It didn't, and that is issue #1.

---

## The issues

### 1 · Connection failure was effectively invisible — CRITICAL

**What you saw.** Name typed, both buttons dead grey, and one line of low-contrast text at
the very bottom of the page: *"Connecting to the game server…"* — below the fold on a
phone, easy to miss on a laptop, and it never changed no matter how long you waited.
Socket.IO retries forever and says nothing, so a misconfigured deployment is
indistinguishable from a frozen page.

**Why it matters more than the deployment.** Any player who opens the game when the server
is asleep — which on a free tier is *most first visits* — gets this. It would have looked
broken to your friend in Addis too.

**Fixed.** A banner at the top of the page, above everything:

> **CAN'T REACH THE SERVER** — The game needs its server, and nothing is answering at
> `http://localhost:3001`.

It names the address it is actually calling, which diagnoses the whole class of problem at
a glance: seeing `localhost` on a deployed site tells you `NEXT_PUBLIC_SERVER_URL` was
never set. When it detects that specific case it says so directly, and reminds you the
value is compiled in at build time so a redeploy is required. Otherwise it explains that
free instances sleep and this may clear itself in ~30 seconds.

It distinguishes *connecting* (first four seconds, normal) from *cannot connect*
(something is wrong).

### 2 · A brief disconnect destroyed a live game — CRITICAL

**The bug.** `drop_empty_rooms()` deleted any room with no connected sockets, and ran on
every disconnect. If both players blinked out at the same moment — shared wifi, a phone
changing network, a server hiccup — the room was deleted between them.

**Evidence.** Reproduced directly against the room model:

```
mid-game: round 1, Lensa has 170 pts
after BOTH briefly disconnect -> room still exists? False
```

170 points and a live round, gone, unrecoverable. On the connection this game is
explicitly designed for, this was a matter of time.

**Fixed.** A room now survives 15 minutes with nobody connected before it is reaped.
Player ids are durable, so the room only has to outlive the outage:

```
both dropped -> room survives? True
Lensa reconnects -> score 170, round 1
```

### 3 · A wrong room code stranded you forever — HIGH

Typing a bad code, or opening a stale link, showed *"No room with that code"* for five
seconds, after which the message vanished and you were left on **"Joining ZZZZ…"**
permanently, with no way out but editing the URL.

**Fixed.** The error persists, and a **Back to the start** button appears beneath it.

### 4 · No way to leave a room — HIGH

Zero exit affordances anywhere in the room. Once in, the only escape was the browser's
back button or retyping the URL.

**Fixed.** A **Leave** control in the room's top bar.

### 5 · Errors self-destructed after five seconds — MEDIUM

Every server error cleared itself on a timer, including ones that required a decision
("That game has already started", "Need at least two players"). Read it too slowly and the
game simply looked inert.

**Fixed.** Errors persist until dismissed or replaced, with an explicit Dismiss control.

### 6 · "Create room" could be double-tapped into two rooms — MEDIUM

No in-flight guard. A double tap — easy on a phone, likelier on a slow connection where
nothing appears to happen — emitted `room:create` twice and created two rooms, navigating
you into the second while your friend might have the code for the first.

**Fixed.** The button disables and reads "Creating…" while in flight, and releases after
six seconds so a failed attempt doesn't lock it forever.

### 7 · A finished game left its timer running — LOW

`finish_game()` never cancelled the round's answer-window task, so it outlived the game.
Harmless in a short session, an accumulating leak on a long-lived server.

**Fixed.** `finish_game()` cancels it.

### 8 · Autofocus threw the keyboard over the timeline on mobile — LOW

The artist field autofocused the moment your turn began, so on a phone the keyboard
covered the timeline you needed to tap.

**Fixed.** Removed. The field is the first thing on the card; you can tap it when ready.

### 9 · The connection banner didn't escalate — introduced, then caught

My first version of fix #1 re-armed its grace timer on every `connect_error`. Socket.IO
retries every few hundred milliseconds, so the deadline was pushed back indefinitely and
the banner sat on "connecting" forever — the exact state it exists to escape.

Caught by looking at the rendered page rather than trusting the code. The timer is now
armed once and cleared only by a successful connect.

## What I deliberately did not change

- **The design.** You said fix the UI and then said nothing works; this pass is about the
  second thing. The layout from the last pass is untouched apart from the new banners.
- **The two-font pairing.** Abyssinica SIL and Noto Sans Ethiopic both cover Ge'ez *and*
  Latin, which is why bilingual lines stay at one apparent size. That should survive any
  redesign.
- **The unverified deck years.** Still yours to fix, and still the thing standing between
  this and a fair game.
- **Free-tier cold starts.** A sleeping server still takes ~30 seconds to wake. The banner
  now explains that instead of hiding it.

---

## Still open, honestly

- **The Docker image has never been built.** No Docker daemon on this machine. The first
  deploy is its first real test; if it fails it will be at the deck-import line.
- **A server restart still ends a game in progress.** Live round state is in memory and
  SQLite sits on the container's own disk. Acceptable for a half-hour session; fixable
  with a volume if it starts to matter.
- **Two players who both close the tab for over 15 minutes lose the room.** That is the
  new grace period, and it is a deliberate trade against rooms accumulating forever.

---

## What to do next

1. Deploy the server (Render blueprint is the browser-only path — see
   [DEPLOY.md](DEPLOY.md))
2. Set `NEXT_PUBLIC_SERVER_URL` on Vercel **and redeploy** — the banner will tell you if
   you forget the redeploy
3. Set `CORS_ORIGINS` on the server to your Vercel origin

If any step is wrong, the app will now say which one rather than sitting there looking
broken.
